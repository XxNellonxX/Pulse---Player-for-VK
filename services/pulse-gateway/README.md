# Pulse Gateway

Серверный комплект для общей версии Pulse. Плеер обращается к одному HTTPS-адресу; слушателю не нужны собственные ключи SoundCloud или прокси. Ключи приложения находятся только в окружении процесса на VPS. Сервер использует официальный API SoundCloud и публичные метаданные MusicBrainz. Он не снимает ограничения доступа, подписки, DRM или географии и не гарантирует наличие конкретной записи.

Комплект развёрнут на пилотном Ubuntu 24.04 VPS: Docker, Compose, публичный DNS и валидный HTTPS проверены. MusicBrainz и поиск SoundCloud отвечают, но непрерывное проигрывание пока не подтверждено: официальный `/streams` нестабильно возвращает 500/503. Установка своего экземпляра требует VPS, домена и действующего доступа приложения SoundCloud. Нужны допустимые условия использования API и разрешённое провайдерами использование аудио в публичном приложении.

## Что арендовать

- Linux VPS с Docker Engine и Compose v2, обычная публичная IPv4/IPv6-сеть, исходящие HTTPS/DNS, доступ к SoundCloud и MusicBrainz из региона сервера.
- Для начальной проверки: 1–2 vCPU и 1–2 ГиБ RAM, 10–20 ГиБ диска, домен с управляемыми DNS. Размер зависит прежде всего от одновременных слушателей и исходящего трафика. Это ориентир для пилота, не измеренная ёмкость или гарантия.
- Публичный TCP 443 для HTTPS и TLS-ALPN проверки сертификата. UDP 443 нужен только для HTTP/3. SSH следует ограничить своим адресом. Порт 8080 остаётся на `127.0.0.1`; порт 80 в этом комплекте не нужен.
- Действующие Client ID/Client Secret зарегистрированного приложения SoundCloud. Вписывать их в пользовательский EXE, Git, Dockerfile, публичную документацию или сообщения нельзя.
- Подтверждённые квоты именно вашего приложения в кабинете SoundCloud. Общие квоты расходуются всей аудиторией, а не выделяются заново каждому слушателю. Для планирования сверяйте актуальные ограничения на выдачу токенов и потоков с кабинетом и [официальной страницей лимитов](https://developers.soundcloud.com/docs/api/rate-limits); поднятие лимитов нашего сервера не увеличивает квоту SoundCloud.

  Для пилота ориентируйтесь примерно на 1500 stream-запросов за 24 часа на приложение, пока кабинет не подтвердит другую квоту; старые упоминания 15 000 не следует закладывать в бюджет. Это ориентир для планирования, а не подтверждённый в этой среде лимит выданных ключей. Повторное получение `/streams`, попытки восстановления и число слушателей расходуют общую квоту. У выдачи токенов также есть отдельные ограничения.
- Проверьте лимит исходящего трафика у хостера. При 160 кбит/с час прослушивания передаёт около 72 МБ аудио; 1000 часов — около 72 ГБ без накладных расходов. Здесь сервер получает аудио и затем отправляет слушателю, так что политика учёта трафика имеет значение. Цена зависит от тарифа и региона; фиксированной цены комплект не обещает.

Отдельный сервер базы данных не требуется. В памяти держатся ограниченные метаданные, токены и временные ссылки. Подписки на артистов и библиотека остаются на устройстве слушателя, а приложение обновляет метаданные при подключении. Сервер получает IP, поисковые запросы и идентификаторы нужных записей, но не хранит список подписок и не присылает обновления, когда плеер закрыт.

## Установка на Linux VPS

1. Создайте DNS A/AAAA `music-api.ваш-домен` на VPS. Запись AAAA публикуйте только при рабочем IPv6. Скопируйте эту папку на сервер, например `/opt/pulse-gateway`.
2. Войдите в неё и создайте приватный файл окружения. В нём находятся реальные секреты; редактируйте файл на сервере, не отправляйте его в чат.

```sh
cd /opt/pulse-gateway
umask 077
cp .env.example .env
chmod 600 .env
nano .env
```

3. Укажите одинаковый домен в `PULSE_DOMAIN` и HTTPS-адрес в `PUBLIC_ORIGIN`, почту для сертификата и MusicBrainz, ключи SoundCloud. Не используйте IP вместо домена. Не ставьте перед Caddy CDN/другой прокси без отдельной настройки доверенных адресов: текущий контракт привязывает медиа-сессию к публичному IP клиента.
4. Проверьте конфигурацию и запустите сервис. `docker compose config` выводит секреты из `.env`, поэтому ниже используется только тихая проверка.

```sh
docker compose config --quiet
docker compose build --pull
docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile
docker compose up -d
docker compose ps
```

5. Проверьте доступность, затем реальные API/первый ресурс HLS.

```sh
curl --fail https://music-api.ваш-домен/healthz
curl --fail https://music-api.ваш-домен/readyz
docker compose exec gateway node src/probe.mjs
```

`healthz` означает, что процесс отвечает. `readyz` означает, что конфигурация прошла начальную проверку; поле `providersVerified:false` намеренно остаётся явным. Эти endpoints не подтверждают действительность ключей, квоты, каталог и проигрывание. Probe делает поиск «Кишлак» и «Капля испуга», получает HLS и первый указанный ресурс, затем проверяет MusicBrainz. Похожее название может относиться к другой записи; совпадение проверяется отдельно. Probe не доказывает полное непрерывное проигрывание.

Другие поисковые строки можно передать аргументами:

```sh
docker compose exec gateway node src/probe.mjs "Капля испуга" "другая запись"
```

6. После успешной проверки установите этот публичный адрес в конфигурацию сборки Pulse `PULSE_GATEWAY_URL`. Сам адрес публичен; общего «секретного» токена в EXE нет. Соберите Windows/macOS из одной версии исходников. Данные профиля приложения и его идентификатор не меняются.

Compose использует `network_mode: host`, рассчитанный на обычный Linux VPS. Этот способ не предназначен для Docker Desktop на Windows/macOS. Слушатель шлюза принудительно привязан к loopback; Caddy подключается к нему по `127.0.0.1:8080`. Файл `.env` исключён из Docker build context и Git. Владельцы root/Docker на сервере всё равно имеют доступ к окружению контейнера — это не защита от администратора VPS. Перед публичным запуском закрепите проверенные digest образов и настройте системные обновления и резервную копию приватного `.env`/сертификатов.

## API для общего нативного клиента

Только `GET` и `HEAD`, тело запроса запрещено. Клиент не отправляет VK cookies, VK tokens, Client Secret SoundCloud или библиотеку пользователя. Ошибки — JSON `{ "error": "короткий_код" }`, при ограничениях есть `Retry-After`. Неизвестные и дублирующие query-параметры отклоняются.

| Endpoint | Ответ |
|---|---|
| `/v1/musicbrainz/search?query=...&offset=0` | Сырой JSON поиска MusicBrainz `artist`, лимит 20; `query` — уже сформированный ограниченный Lucene-запрос клиента |
| `/v1/musicbrainz/artist/<uuid>` | Сырой JSON карточки `artist`, `inc=url-rels+tags` |
| `/v1/musicbrainz/artist/<uuid>/releases?offset=0` | Сырой JSON `release-group` по артисту, лимит 30 |
| `/v1/soundcloud/tracks?q=...&limit=30&linked_partitioning=true` | JSON официального поиска, `access=playable`; допускаются ограниченные `offset`/`cursor` |
| `/v1/soundcloud/tracks/<id-or-urn>` | JSON официальной карточки трека |
| `/v1/soundcloud/resolve?url=...` | Карточка по публичной ссылке `soundcloud.com` / `on.soundcloud.com`; приватные query/capability ссылки не принимаются |
| `/v1/soundcloud/tracks/<id-or-urn>/streams` | Только поддерживаемые `hls_aac_160_url` / `hls_mp3_128_url`, заменённые адресами этого шлюза |
| `/v1/media/<48 hex>/<index>` | Зарегистрированный manifest/ключ/сегмент; URL назначения нельзя указать клиентским параметром |

Пагинация SoundCloud `next_href` переписывается на этот же публичный origin. Медиассылки имеют случайный токен 192 бита, срок 15 минут и привязку к IP. В HLS переписываются варианты, ключи, maps и сегменты; неподдерживаемые внешние steering/asset URI отклоняются. Исходное шифрование HLS сохраняется, DRM не расшифровывается. Если сессия истекла, IP сменился или запись вытеснена, ответ `410` требует заново получить `/streams` через штатное разрешение источника плеера. Адреса audio/CDN, подписанные query и токены не записываются на диск и не логируются.

## Ограничения и эксплуатация

- Разрешены только точные API-маршруты SoundCloud/MusicBrainz и официальный SoundCloud CDN. Произвольного proxy/fetch URL, uploads и пользовательской авторизации API здесь нет.
- Каждый исходящий адрес и каждый редирект проверяются. DNS-ответ с локальными/служебными IPv4/IPv6 отклоняется; валидированные адреса закрепляются в TLS lookup. OAuth передаётся только `api.soundcloud.com`, Basic — только `secure.soundcloud.com/oauth/token`. CDN не получает эти заголовки.
- Client credentials: HTTP Basic + `grant_type=client_credentials`. Refresh: документированная форма с `refresh_token`, `client_id`, `client_secret`, без Basic. Есть reuse, single-flight, ротация refresh, одна попытка восстановления и cooldown. После рестарта токены пропадают; не перезапускайте сервис часто, у выдачи токенов есть квоты провайдера.
- MusicBrainz: глобально не более одного нового upstream-запроса в секунду; shared cache поиска/карточек 6 часов, релизов 1 час. SoundCloud: метаданные 5 минут. Кеш метаданных ограничен 256 записями / 32 МиБ и очищается при рестарте.
- Аудиосегменты: отдельный RAM-кеш до 64 МиБ / 128 записей, только внутри действующей media capability (не более 15 минут). IP, capability, полный подписанный URL и Range входят в область доступа/ключ кеша. Манифесты, ключи шифрования и ошибки не кешируются. Попадания не продлевают срок; истечение или удаление capability удаляет её сегменты. После нового успешного `/streams` та же ещё действующая capability может использоваться повторно для того же IP, трека и точного списка URL. Аудио на диск не записывается.
- В клиенте ограниченный RAM-кеш до 128 МиБ ускоряет повторные запросы в текущем сеансе, пока действителен источник. Это не постоянная копия всей библиотеки и не гарантия мгновенного запуска после перезапуска. [Условия SoundCloud API](https://developers.soundcloud.com/docs/api/terms-of-use) допускают только необходимый session-based cache, запрещая постоянное хранение User Content. Собственные локальные файлы Pulse хранятся отдельно.
- Relay хранит максимум 8 МиБ одного ответа в памяти, до 16 операций одновременно по умолчанию. JSON — до 2 МиБ, HLS — до 1 МиБ. Сетевые запросы и redirects имеют ограничения времени/числа переходов. Размер сегмента выше лимита даёт явную ошибку, не неограниченное скачивание.
- SoundCloud API использует документированный URN и собственный User-Agent Pulse. На явный HTTP 500/502/503/504 у GET есть один повтор через 500 мс, с общим бюджетом для redirects/auth и прежним access token; 429/403/404 и сетевые исключения не повторяются. DNS входит в бюджет исходящего запроса. Наличие повтора не гарантирует восстановление провайдера.
- Default abuse caps: 60 metadata и 600 media запросов/мин/IP, 6 операций/IP, 6000 запросов/мин глобально, 120 МиБ media/мин/IP и 2 ГиБ/мин глобально. Реестр capability: 512 сессий, до 8 свежих/IP, 2048 адресов/сессию и 16 МиБ всех URL. Старые сессии вытесняются. Это защита от случайной/умеренной нагрузки, а не замена DDoS-защите и провайдерским квотам.
- Публичный endpoint можно вызвать вне Pulse. Секрет из EXE не решает эту задачу. При росте аудитории понадобятся измерение нагрузки, уменьшение квот, бюджет/алерты по трафику, а при необходимости реальная авторизация пользователей или защита на стороне хостера. Не поднимайте лимиты без проверки памяти и квот SoundCloud.
- В приложении и Caddy нет access log: в пути запроса содержится capability. В Caddy также исключён `http.log.error`, поскольку записи ошибок reverse proxy могут содержать URI. TLS/startup диагностика сохранена; изолированный настоящий Caddy проверен с недоступным upstream и фиктивным media URI. Не включайте debug, логи полных URL, тел/заголовков ответа, OAuth или поисковой библиотеки. Для мониторинга используйте uptime, ресурсы процесса, суммарные коды ошибок/трафик без путей и секретов.
- Обновление: сохраните `.env` и Caddy volumes, затем `docker compose build --pull && docker compose up -d`. Смена кода не затрагивает профили Pulse. Обновление/рестарт сбрасывает transient cache и media sessions, поэтому текущий клиент должен заново разрешить временную ссылку.

## Проверка исходников и реальные пределы

```sh
npm test
# Только из полного checkout репозитория Pulse:
node --test ../../qa/gateway-security-independent.test.mjs ../../qa/gateway-transport-independent.test.mjs ../../qa/gateway-http-independent.test.mjs
```

Собственные тесты проверяют форматы OAuth, параллельную выдачу/обновление токенов, cooldown, cache/квоты, глобальный MusicBrainz интервал, срок capability, перепись HLS, DNS pinning и ограничение ответа. Независимые тесты из `qa/` вызывают настоящий HTTP handler на loopback с подставленным upstream: API allowlist, пагинацию, HLS, ключи, диапазоны, смену IP, истечение/рестарт, безопасные ошибки и ограничения частоты. Подмена транспорта — только программная dependency injection тестов; настройки production не позволяют подставить произвольный upstream-host.

Локально проверено на Node 24, на пилотном Ubuntu 24.04 — настоящий Docker build и 26 тестов внутри Node 22 контейнера; Caddy validate и внешний HTTPS прошли. Реальные ключи перенесены по SSH в приватный `.env`, в исходники и артефакты не включены. MusicBrainz и поиск SoundCloud возвращают 200. Прямые запросы `/streams` с VPS получали как 200, так и 500 `Middleware error`/503; до устойчивой выдачи HLS и декодирования аудио проигрывание не считается проверенным. Перед публичным релизом нужны тесты воспроизведения на Windows и физическом Mac, длительное прослушивание/переключение/seek, а также смена сети, 429/403, рестарт и нагрузка.

Страница [регистрации SoundCloud](https://developers.soundcloud.com/docs/api/register-app) проверена 22 октября 2026 года: Artist Pro, собственное зарегистрированное приложение и пара Client ID/Secret, обмен на access token, секрет только на сервере. Browser-регистрация остаётся допустимой альтернативой CLI. Подтверждённая авторизация/поиск не гарантируют разрешение каждого аудиопотока. Наличие результатов каталога не гарантирует исходный файл, точную версию или доступность любого трека.
